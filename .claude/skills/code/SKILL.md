# Code Skill

## Goal

根据已确认的需求和方案完成代码实现，并通过必要的验证确保修改正确。

## Core Rules

1. **先确认上下文，再修改**

   - 理解当前需求、已有方案和相关代码。
   - 不确定时先搜索/阅读代码，不凭猜测修改。
   - 只读取与当前任务相关的文件，避免无目的扫描整个项目。

2. **严格按照方案实现**

   - 优先执行已经确认的技术方案。
   - 如果实现过程中发现方案存在明显问题，先说明问题和调整方案，再继续。
   - 不擅自扩大需求范围。

3. **最小化修改**

   - 优先修改已有代码，不重复实现已有能力。
   - 复用现有组件、工具函数、状态管理、API 和类型。
   - 不进行与当前需求无关的重构、格式化或架构调整。
   - 不为了“看起来更优雅”而增加不必要的抽象和依赖。

4. **遵循项目现有规范**

   - 遵循项目已有的目录结构、命名、组件设计、状态管理、请求方式、类型定义和代码风格。
   - 优先参考项目中已有的类似实现，而不是自行设计一套新模式。

5. **保持代码质量**

   - 类型完整，避免无意义的 `any`。
   - 正确处理错误、空值、边界条件和异步状态。
   - 避免明显的重复代码、隐式副作用和不必要的复杂度。
   - 不为了通过类型检查而使用不合理的类型断言。

6. **修改后必须验证**

   - 根据项目实际情况运行相关的类型检查、Lint、测试、构建或其他验证命令。
   - 优先验证本次修改直接影响的功能。
   - 如果无法执行某项验证，明确说明原因。
   - 不声称“已验证”除非实际执行过。

7. **遇到问题先定位根因**

   - 不通过不断试错堆代码解决问题。
   - 出现报错时，先判断问题属于代码逻辑、类型、依赖、环境、配置还是数据。
   - 优先修复根因，而不是增加临时补丁。

## Implementation Flow

Understand
→ Locate relevant code
→ Implement
→ Review changes
→ Run verification
→ Fix issues
→ Report result

## Scope Control

- 小改动：直接完成实现并进行必要验证。
- 中等改动：按照方案逐步实现，并验证关键路径。
- 大型改动：分阶段实现，每完成一个关键阶段进行验证。
- 涉及公共组件、公共 API、数据结构、状态模型或核心架构时，提高验证标准。

## Output

完成后简洁说明：

- 修改了什么
- 关键实现方式
- 验证了什么
- 是否存在未解决问题
- 如有必要，列出后续注意事项

## Boundaries

本 Skill 负责**代码实现与验证**。

不负责：

- 重新制定完整技术方案
- 无关代码重构
- 自动扩大需求范围
- 自动生成变更日志

重大需求的变更日志由独立的 Log Skill 处理。
