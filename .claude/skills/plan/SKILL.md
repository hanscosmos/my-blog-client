# Planning Skill

## 目标

在修改代码之前，分析需求、理解现有代码库并制定可执行的技术方案。

**本 Skill 只负责分析和规划，不直接修改代码。**

---

## 核心规则

### 1. 先理解，再方案，再编码

收到需求后，不要立即修改代码。

先：

1. 理解需求和验收标准
2. 检查相关代码和项目结构
3. 分析现有实现和数据流
4. 判断影响范围
5. 制定方案
6. 分析风险
7. 拆分实施步骤

方案得到用户确认后，才进入 Coding 阶段。

### 2. 基于实际代码制定方案

不要凭经验猜测项目结构、数据流或业务逻辑。

优先查找：

- 相关页面 / 组件
- Store / Hooks / Composables
- API
- 类型定义
- 路由
- 类似功能

如果代码或文档无法确定某个关键事实，不要猜测，应询问用户。

### 3. 优先复用，最小修改

优先：

> 复用现有实现 > 扩展现有实现 > 新建实现

避免：

- 不必要的新依赖
- 不必要的新抽象
- 无关重构
- 修改与需求无关的代码

### 4. 遵循现有架构

方案必须优先符合项目已有的：

- 文件组织
- 编码风格
- 状态管理
- API 模式
- 类型体系
- 组件设计
- 测试方式

不要为了所谓“最佳实践”随意改变现有架构。

### 5. 方案需要考虑风险

根据实际需求分析：

- 影响范围
- 数据兼容性
- 状态变化
- API 变化
- 边界情况
- 潜在副作用

不需要机械罗列与需求无关的风险。

## 任务规模

### 小需求

简单、低风险、影响范围明确的需求，可以简化分析。

### 中大型需求

涉及多个模块、公共组件、API、数据结构、状态管理、权限或架构变化时，进行完整分析。

---

## 最终原则

**不要为了输出完整方案而进行无意义的分析。**

方案应该：

> 足够详细，可以指导 Coding
> 足够简洁，不制造额外上下文成本
> 基于代码，而不是基于猜测
