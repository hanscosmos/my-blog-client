## 需求背景

评论功能上一次落地时只支持纯文本（`Input.TextArea` + `maxLength=500`），当时明确把「表情 / 图片 / 加粗」记进了遗留项。本次要求补上：

- 用 **markdown 编辑器**发表评论，但「简易一些，功能不用太全」
- 基础能力要有：**加粗、表情、上传图片、链接**
- 另外在实测过程中发现上传图片会被踢回登录页，要求一并排查

## 关键发现与分析

### 1. 上传图片被踢回登录页 —— 两层原因叠加

**触发条件：access token 只有 30 分钟**

`my-blog-service` 的 `.env` 里 `ACCESS_TOKEN_WORK_TIME=0.5`（小时），`TOKEN_WORK_TIME=720`（refresh token 30 天）。

关键区别在于后端的鉴权中间件（`middleware/auth.py`）：

```python
if url_path.startswith('/client/'):
    return          # ← /client/* 整体跳过全局 JWT 校验
v_result = validate_token(request)
```

- `/client/comment/*` 跳过中间件，鉴权由视图内部调 `get_user_id` 决定 → 评论列表**匿名也能看**
- `/sys/file/upload` 不在白名单、也不以 `/client/` 开头 → **走全局 JWT 校验**，token 过期就返回 401

而登录态是 `useAuth` 用 zustand `persist` 存在 localStorage 的，`isLogin` 不会自己过期。所以 token 早已失效时，页面照常显示已登录、评论表单照常渲染，完全看不出异常。

**真正的崩溃点：`request.ts` 的刷新逻辑写错了**

```js
// 修复前
const refreshRes: any = await instance.post("/user/refresh", {...});
if (refreshRes.code === 0 && refreshRes.data?.token) { ... }
```

但**这个响应自己也要过一遍同一个拦截器**，而拦截器最后是 `return res.data` —— `refreshRes` 拿到的已经是解包后的 `{ token }`，不是 `{ code, msg, data }`。于是 `refreshRes.code` 是 `undefined`，`undefined === 0` 恒为 false，**永远走 else 分支登出 + 跳登录页**。

刷新 token 的 HTTP 请求其实成功了、新 token 也拿到了，客户端却把它当失败丢掉。**这条路径从来没生效过**。

> 同一个 bug 也会打中「发表评论」：token 过期后 `/client/comment/add` 里的 `get_user_id` 返回 None → 401 → 同样跳登录页。只是恰好在传图时先撞上。

**结论：没有新增前台上传接口。** 上传要求登录是符合预期的（评论本身也要求登录），加 `/client/file/upload` 会有两个问题：① 不解决真正的问题，刷新逻辑坏着照样被踢；② `/client/` 会跳过中间件，等于开一个**匿名上传到 COS 的入口**，而后端不校验类型和大小。

### 2. 技术选型：不引入第三方 markdown 编辑器

需求只有 4 个按钮，`@uiw/react-md-editor` 这类库会带来打包体积和样式割裂的代价，定制工具栏反而更麻烦。改为**自研轻量工具栏**基于 antd `Input.TextArea`。

**唯一新依赖是 `remark-breaks`**（约 1KB 的官方 remark 插件）。

### 3. `remarkBreaks` 的副作用 —— 踩过的坑

项目原有的文章渲染没有用 `remark-breaks`，但**评论必须用**：历史评论是纯文本，当初靠 CSS 的 `whitespace-pre-wrap` 保留换行，改成 markdown 渲染后如果不补这个插件，所有老评论的换行都会塌掉。

但它有个容易搞错的后果：**单个换行会被渲染成 `<br>`，不是段落边界**。

这直接影响「图片是否独占一行」的实现——markdown 渲染出的 `<img>` 默认是**行内元素**，光标停在文字中间点上传会存成 `文字![图片](url)文字`，一张 240px 的图会把整行行高撑开、两侧文字贴着图片底边对齐。第一版补了单个 `\n`，验证时发现渲染成了：

```html
<p>看看这个<br/>
<img src="..." /></p>
```

图片仍和文字在同一个 `<p>` 里，还平白多出一个空行。**markdown 里只有空行才是段落边界**，必须补 `\n\n`。

修复后又发现「打字 → 回车 → 插入图片」这个很常见的操作会存下两个空行，最后把边界归一化成「恰好一个空行」。

### 4. XSS 策略：靠渲染侧根治，后端不加 sanitize

- **不启用 `rehype-raw`** → markdown 里的原始 HTML 被当作纯文本转义输出
- react-markdown 默认的 `urlTransform` 会拦掉 `javascript:` 之类的危险协议
- 实测确认：`<script>alert(1)</script>` 输出为 `&lt;script&gt;...`，`[x](javascript:alert(1))` 的 href 被清空

因此后端**不需要**额外的过滤层（符合最小改动）。另外 `my-blog-admin` 里没有任何评论相关文件，不存在第二个渲染消费方。

### 5. `react-markdown` 会透传 `node` 属性

`react-markdown` 用了 `hast-util-to-jsx-runtime` 的 `passNode: true`，自定义组件会额外收到一个 `node`（AST 节点）。整体 `{...props}` 展开到 DOM 上会变成非法属性。且 ESLint 的 `no-unused-vars` 会报解构出来的 `_node` 未使用，所以最终**逐个取用属性**而不是解构剩余。

> 顺带发现：`ArticleDetail.tsx` 的 `img` 组件就是整体展开的写法，存在同样的问题（未修，属无关范围）。

### 6. 样式复用方式

评论内容与文章正文的元素范围一致，直接复用已有的 `.article-content`（代码块、引用、列表、表格都现成），只新增 `.comment-content` 覆盖字号与间距。覆盖**依赖 `index.css` 的引入顺序**（`comment.css` 在 `article.css` 之后），因为两者选择器特异性相同。

### 7. 后端字段与迁移方式

`Comment.content` 是 `CharField(max_length=500)`，而 markdown 源码里一条 CDN 图片 URL 就占 60-70 字符，放几张图就爆。改为 `TextField`，`MAX_CONTENT_LENGTH` 500 → 2000。

**迁移方式：手工 ALTER TABLE，不引入 migration。** 因为 `modules/comment/` 根本没有 `migrations/` 目录（整个仓库只有 `modules/authority` 有），说明 `blog_comment` 表不是通过 Django migration 建的；此时跑 `makemigrations` 会生成建表迁移并撞上已存在的表。

```sql
ALTER TABLE blog_comment MODIFY COLUMN comment_content LONGTEXT NOT NULL;
```

### 关键实现点

**`MarkdownEditor`**

- 光标操作必须拿到 antd 藏在 `resizableTextArea` 里的原生 textarea
- `insertAtCursor(before, after, hint)`：有选区就包裹选区，无选区就插入占位文字并选中它
- 受控组件要把 `.setSelectionRange` 放进 `requestAnimationFrame`，否则会被这次渲染覆盖
- 图片：上传成功后按「恰好一个空行」的规则补位，让图片独立成段（源码干净，不依赖 CSS 补救）
- 支持 Ctrl+V 粘贴截图；剪贴板同时有文字时不拦截，避免吃掉正常文本粘贴
- 编辑 / 预览切换，预览复用 `MarkdownContent`

**`MarkdownContent`**

- `remarkGfm` + `remarkBreaks`，不做代码高亮和标题锚点（评论不需要）
- `img` 逐个取用 `src/alt/title` 并加 `loading="lazy"`；`a` 加 `target="_blank" rel="noreferrer"`
- 不启用 `rehype-raw`

**`request.ts` 的修复**

```js
// 修复后：拿到的已经是解包后的 data（{ token }），不能再按外层信封判断
const refreshRes = await unwrapResponse<{ token?: string }>(
  instance.post("/user/refresh", { refreshToken: store.refreshToken })
);
const newToken = refreshRes?.token;
```

复用了文件里已有的 `unwrapResponse`（它的 JSDoc 写的就是「拦截器改变了返回值形状」这件事）。

## 后续注意事项

1. **必须执行 ALTER TABLE** 并重启 Django 服务，否则带图片的长评论插入会失败
2. **`/sys/file/upload` 对任意登录用户开放**，且后端**不校验文件类型与大小**。前端那点校验只是体验层，不是安全边界。后台的图片/头像/文章封面和前台评论图片共用这一个接口，将来要收紧的话改动点在 `modules/system/views/other.py` 和 `config/permission.py`
3. **潜在耦合**：`/sys/file/upload` 一旦被登记进 `PERMISSION_PATH_MAP`，游客上传就会变成 403。到那时需要拆一个真正的 `/client/file/upload`（但**必须要求登录**）
4. **字数语义变了**：现在计的是 markdown 源码字符数，一张图约 70 字，用户实际能写的字变少
5. **历史纯文本评论的兼容代价**：以 `#`、`-`、`*` 开头的行会被当作 markdown 语法解析，无法避免
6. 极端情况：`[x](javascript:alert(1))` 会渲染成 `href=""`，点一下刷新当前页（无 XSS）。要消除可改成无有效 href 时渲染纯文本
7. `MarkdownEditor` 的 `maxRows` 默认 8（原来是 6），因为工具栏多占一行
8. 表情有选区时是「插在选区前并保留选区」，不是替换选中内容

## 减少 token 消耗的建议

1. **跨前后端排查先打 curl 再读代码**。本次 `curl -X POST http://127.0.0.1:8000/sys/file/upload` 一条命令就确认了 401 的响应信封结构，比读一遍中间件+视图+拦截器快得多
2. **前后端分开派子 agent 并行探索**。本次两个 Explore agent 分别啃前端评论链路和后端接口，主上下文只收到结论，没有被几十个文件的源码占满
3. **验证渲染类改动用 Node + `renderToStaticMarkup` 跑断言**，比在浏览器里手点更快、更确定，还能给出「源码 → HTML」的对照
4. **改了原子类不要去 grep 整个项目**，直接查构建产物 `dist/assets/*.css` 确认类名是否真的生成（UnoCSS 是按需生成，拼错的类名不会报错、只会静默失效）
5. 排查这类「页面看起来正常但操作突然失败」的问题时，优先怀疑**持久化的登录态**，而不是失败的那个操作本身
