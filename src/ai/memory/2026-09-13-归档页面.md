## 需求背景

博客前台需要新增「归档」页，与首页、关于同级放在顶部导航栏。要求：

1. 文章按时间倒序、以年为单位分组
2. 标签统计（每个标签的文章数量），点击筛选、再次点击取消筛选
3. 草稿和「仅自己可见」的文章不展示
4. 需要新增后端接口，允许修改后端代码

## 关键发现与分析

### 后端已有可复用资产

`modules/client/views.py` 里已存在 `get_article_count_by_tag`，注册在 `POST /article/stat/tag`，但**两个前端（client / admin）都没有任何调用方**（已 grep 确认）。它有两个缺陷：

- 没有过滤 `status` / `visible`，草稿和私有文章也被计入
- 只返回 `{ id, name, count }`，缺 `alias`

因此决策为**改造复用**而非新建，同时顺手修掉缺陷。用户已确认此方案。

### 可见性过滤的口径差异（重要）

- `POST /article/list`（首页）对**已登录作者**额外放行自己的私有文章：`Q(visible='public') | Q(visible='private', author=user_id)`
- 归档页要求更严格，**无论是否登录，草稿和私有都不展示**。两者口径不同是刻意的，已写入 `docs/PROJECT.md`

### 排序陷阱

`Article.Meta.ordering = ['-isTop', '-createTime']`。归档要纯时间序，必须显式 `.order_by('-createTime')` 覆盖，否则置顶文章会乱序。

### 性能与字段裁剪

`ArticleSerializers` 每条文章都要额外查分类、父分类、作者、标签关系、标签（N+1 严重）。归档列表用不上这些字段，改用 `sql.values('id', 'title', 'createTime')` 直接返回，避免序列化器开销。

### 关键决策

| 决策点 | 选择 | 原因 |
|---|---|---|
| 归档列表分页 | **不分页** | 个人博客量级小；归档语义就是一次看全量，年份分组不会被分页打断。将来量大了加 `pageNumber/pageSize` 即可，前端分组逻辑无需改动 |
| 标签筛选位置 | **服务端过滤** | 对齐 `/article/list` 的「过滤参数」范式，列表 payload 更瘦；代价是切换标签需重新请求 |
| 筛选参数 | 标签 `id`（非 `alias`） | 直接对应 `ArticleTagRelation.tag`，无需额外查表 |
| 请求时机 | 标签统计挂载时拉一次；切换筛选只重拉列表 | 两个请求互不依赖，可并行 |

## 后续注意事项

### ✅ `services/request.ts` 的两处存量问题（同日已修复）

归档功能完成后，`pnpm build` 是失败的、`pnpm lint` 也是失败的，两处问题都在 `src/services/request.ts`，与归档改动无关，已单独修复。

**问题 1 — 4 个 `TS2322`**（`createRequest` 的 4 个方法）

```
error TS2322: Type 'AxiosResponseResult<any, T, any, any>' is not assignable to type 'T'.
'T' could be instantiated with an arbitrary type which could be unrelated to ...
```

**根因**：`package.json` 写 `^1.11.0`，实际解析到 **axios 1.20.0**。1.20 重构了实例方法泛型：

```ts
type AxiosResponseResult<T, R, D, P> = R extends AxiosResponseDefault ? AxiosResponse<T, D, {}, P> : R;
```

原代码 `inst.get<any, T>(url)` 想用第二个泛型 `R` 表达「拦截器已解包成业务数据」。当 `R` 是裸类型参数 `T` 时，TS 无法判定 `T extends AxiosResponseDefault`，条件类型保持未解析，而条件类型不能赋给 `T`。

**修复**：承认「拦截器改变了返回值形状」这件事 axios 类型系统表达不了，在**一处**显式断言：

```ts
const unwrapResponse = <T>(promise: Promise<unknown>): Promise<T> => promise as Promise<T>;
// ...
return unwrapResponse<T>(inst.get<ApiResponse<T>>(url, config));
```

调用方签名 `request.post<T>(...)` 完全不变，`.data.data` 的写法依旧不需要。**注意**：不要改回 `inst.post<any, T>(...)`。

**问题 2 — `no-useless-escape`**（`getCookie` 第 25 行）

字符类里的 `\[` 不需要转义（`\]` 才需要）。`\[\]` → `[\]`，逐字符比对 0x00–0x250 确认匹配集合完全一致。

> 踩坑记录：用 Bash heredoc 传含大量反斜杠的脚本时，反斜杠会被吞掉一层，导致 `anchor not unique` 之类的静默失败。改用 `chr(92)` / `String.fromCharCode(92)` 构造反斜杠可绕开。

### 其他

- **`/article/stat/tag` 语义变更**：从「全部标签关联数」变为「前台可见文章数」。已确认两前端此前无调用方，不影响存量功能，但 `docs/PROJECT.md` 已注明
- **归档接口不分页**是确认过的设计，非缺陷
- **参数类型安全**：`tag` 传入非 UUID 字符串会触发 Django `ValidationError`。这一点与现有 `category` 参数的处理方式一致（都未做额外校验），属既有风格，未单独加固

- **首页侧边栏 `TagCloud` 仍是占位**（`tags` 写死为空数组）。本次新增的 `getTagStatApi` 正好可以接通它，属于顺手可做但未做的范围
